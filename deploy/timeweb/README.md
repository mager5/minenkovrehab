# Альтернативный запуск: Cloud Server + три постоянных процесса

**Уточнение этапа 5:** основная подготовленная схема — [App Platform Docker Compose](APP_PLATFORM.md). Официальная документация подтвердила поддержку приватной сети и постоянного worker; дополнительные VM не обязательны. Этот документ сохраняется как альтернативный VM runbook, а его прежнее предположение о worker App Platform больше не актуально.

Подготовка, **не выполненный deploy**. Для альтернативного самостоятельного запуска используется Linux Cloud Server с Docker Engine/Compose v2 и приватной сетью. Timeweb [документирует установку собственной ОС и приватные сети](https://timeweb.cloud/docs/cloud-servers/manage-servers/create-server). Premium NVMe/Ultra имеют приватные сети; Standard — нет. Нужен сервер в совместимой зоне Friendly Halimede. Сам сервер и сеть не проверялись/не изменялись.

Compose запускает worker отдельным бесконечным Node-процессом с restart unless-stopped, SIGTERM/drain, health/readiness и heartbeat в БД. Никакого HTTP запроса для активации worker не требуется. Локальный тест запускает **настоящий queue-worker.js**, ждёт sent синтетического задания, readiness и heartbeat. Docker Compose config также проверен. Healthcheck unhealthy сам по себе не перезапускает живой процесс: настроить внешний мониторинг/оповещение и операторский restart при зависании. При unavailable DB worker продолжает цикл, readiness=503, затем восстанавливается.

## Переменные — значения без секретов

Файлы /etc/rehab/{frontend,backend,worker,migrator}.env создаёт оператор отдельно от Git, chmod 600. Эти файлы сейчас не существуют в проекте и не читались. Секреты ниже задаются приватно; пустые значения должны останавливать запуск. `.env` проекта никогда не копируется. Код не вызывает dotenv.

| Процесс | Переменные |
|---|---|
| Frontend | MIGRATION_ENV=staging; MIGRATION_SITE_ORIGIN=https://stage.example.invalid (заменить отдельным staging origin); MIGRATION_API_INTERNAL_URL=http://backend:3101 |
| Backend | MIGRATION_ENV=staging; MIGRATION_SITE_ORIGIN такой же; MIGRATION_DATABASE_URL=postgresql://rehab_payment:SECRET@PRIVATE_STAGING_HOST:5432/rehab_staging; MIGRATION_AUTH_DATABASE_URL аналогично rehab_auth; MIGRATION_RESET_KEY 32 случайных байта hex; STAGE1_TEST_PASSWORD2 отдельный синтетический секрет; STAGE1_PORT=3101; MIGRATION_VIDEO_PROVIDER=disabled или kinescope |
| Worker | MIGRATION_ENV/site/reset key те же; MIGRATION_DATABASE_URL указывает **тот же staging host/db**, может содержать только placeholder username без application password (URL используется для сравнения); MIGRATION_WORKER_DATABASE_URL с ролью rehab_worker; STAGE1_TEST_PASSWORD2 синтетический, нужен валидатору config, не используется worker; MIGRATION_MAIL_PROVIDER=test; MIGRATION_WORKER_PORT=3102 |
| Migrator | та же isolated config, MIGRATION_MIGRATOR_DATABASE_URL с отдельным владельцем схемы; MIGRATION_MIGRATION_CONFIRM=isolated-rehab-schema |
| Kinescope (только backend) | KINESCOPE_AUTH_SECRET 32 случайных байта hex; KINESCOPE_CALLBACK_USER/PASSWORD отдельные; KINESCOPE_STRICT_AUTH_CONFIRMED=true **только после проверки strict в проекте Kinescope** |
| RuSender (только worker, пока не включать) | MIGRATION_MAIL_PROVIDER=rusender; MIGRATION_MAIL_NETWORK_ENABLED=true; MIGRATION_MAIL_ALLOWED_RECIPIENTS явный allowlist staging; MIGRATION_MAIL_NAMESPACE постоянный идентификатор окружения; RUSENDER_API_TOKEN; RUSENDER_KEY_ID; RUSENDER_FROM подтверждённого домена |

Текущий staging работает только с **test** оплатами. Даже mode=live входящего ResultURL будет отклонён. Строгая проверка суммы/подписи/заказа/режима сохраняется. Checkout создаёт pending order и локальную status URL; реальная Robokassa payment URL/фискальный контракт не включены.

Новая production БД default_db на 192.168.10.4 **не является staging**: config отвергает её. Нужна отдельная пустая rehab_staging, разрешённая оператором в приватной сети, с TLS и CA по политике managed PostgreSQL. Пароль gen_user не используется. Роли приложения не должны быть owner/superuser; роли и TLS smoke проверяются на staging после отдельного разрешения, сейчас только локальные проверки. Backup с реальными данными не входит в build context; staging сначала только synthetic seed.

## Команды и порядок будущего запуска

1. Подготовить отдельные VM/DB, private network, TLS reverse proxy на **отдельном staging hostname**, firewall: public только 443; 3000 loopback, backend/worker только внутренняя Docker network. Не менять рабочий DNS. Reverse proxy не должен писать cookie, Authorization, request body, query tokens в логи. На callback отключить Basic header/body logging. Node image 22-bookworm-slim проверяется локальной сборкой; digest проверенного Node22 образа уже закреплён в Dockerfiles; перед выпуском закрепить immutable release tags приложения.
2. Из чистого checkout migration/timeweb: `docker compose -f deploy/timeweb/compose.yaml build`. Не копировать старые .next/.env. Frontend build использует синтетическую local config без API calls; при запуске runtime env устанавливает staging URL. Локальные образы имеют теги rehab-{frontend,backend}:local; Compose staging теги создаются командой build, push отсутствует.
3. Приватно provision LOGIN роли rehab_payment, rehab_auth, rehab_worker и отдельного migrator. Подготовить их ограниченные env-файлы. Никаких application URLs в shell history/argv. `docker compose -f deploy/timeweb/compose.yaml --profile tools run --rm migrate` применяет 001–005 **в одной транзакции**, advisory lock и ledger/checksums. Повтор безопасен; существующая untracked schema/изменённый SQL отвергается. Затем apply roles.sql на **rehab_staging** migrator-инструментом оператора (только GRANT, никаких production DB). Прямой psql с Мака к production не использовать.
4. Seed только synthetic products/users/videos в staging отдельной проверенной процедурой. Полный архивный import пока имеет намеренный loopback guard и здесь не запускается. Миграции и importer создают schema альтернативными путями: migrate отвергает untracked импортированную schema. Для будущего production импорта потребуется согласованная фиксация ledger в той же import transaction; сейчас не обходить защиту.
5. `docker compose -f deploy/timeweb/compose.yaml up -d backend worker`; проверить backend /health/live, /health/ready, worker /health/live, /health/ready и worker_heartbeat свежий (<30s). Проверить failed count и oldest pending age во всех трёх outbox без выгрузки recipient/ciphertext. Нет реальных писем: sender=test.
6. `docker compose -f deploy/timeweb/compose.yaml up -d frontend`; через TLS проверить /api/health и synthetic login→dashboard→checkout pending→status→logout, reset/confirmation, чужой курс, Kinescope mocked callback. Frontend /api/health проверяет backend; worker отдельно, иначе его остановка незаметна для сайта.
7. Откат образов: сохранить предыдущие immutable tags и DB snapshot. Остановить новые заказы/worker, откатить **совместимые** frontend/backend/worker вместе. SQL автоматически назад не применять; для несовместимой схемы восстановить отдельный snapshot только после разрешения. Рабочий сайт продолжает работать независимо. Полная cutover/дельта — отдельный будущий этап.

## Ограничения внешних интеграций

[Kinescope Authorization Backend](https://docs.kinescope.com/developer-guides/authorization-backend/): публичный HTTPS POST callback /api/kinescope/authorize через Next proxy; Basic credentials, подписанный HS256 drmauthtoken, lifetime 120s, video UUID/user UUID/hash серверной сессии. Callback повторно проверяет активную покупку, соответствующий курс, подтверждённый/не заблокированный аккаунт и действующую сессию. Нужны включённая защита и **strict=true** в Kinescope; при 5xx deny, иначе провайдер может fail open. Flag в приложении — подтверждение оператора, не проверка аккаунта. Provider ID/ready заполняются только после согласования уроков и загрузки (загрузка сейчас не выполнялась). iframe интегрирован для stage video. Старые HTML5 timecode кнопки не управляют iframe; для них потребуется официальный Player SDK. Токен надо получать снова после истечения/перезапуска плеера; бесшовное продление длинного просмотра пока не проверено. Защита не исключает запись экрана, sharing действующей ссылки в течение TTL и уже выданные licenses; реальная DRM/тариф/мобильные браузеры не проверены.

[RuSender Email API](https://rusender.ru/developer/api/email/): POST /api/v1/external-mails/send/{key_id}, Bearer external_mail.send, stable idempotencyKey namespace:kind:job UUID. 200/uuid означает принятие, не доставку. Outbox FOR UPDATE SKIP LOCKED исключает concurrent local claims; повтор после сбоя commit использует тот же provider key. 429/5xx/network retry, Retry-After, exponential 60s…1h, максимум 8 попыток; прочие 4xx/deadletter status=failed. Секреты/пароли в письмах отсутствуют; reset/confirmation links одноразовые, ciphertext очищается после отправки. Адаптер timeout=8s, HTTP redirects запрещены. **Окно хранения idempotencyKey провайдером не указано в документации**: до реальных писем согласовать retention/reconcile при неопределённом ответе. Автоматически перезапускать failed с новым ключом запрещено. Для реального отправителя необходимы verified domain, SPF/DKIM/DMARC, activated key и allowlist. На этом этапе — mock transport/test sender, ни одного сетевого send.
