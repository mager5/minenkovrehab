## Решение по базе

Рекомендация: после подтверждения публичного TLS, постоянного egress IP и Firewall и отдельного разрешения повысить **существующий minenkov-db до тарифа >=2ГБ**, создать rehab_staging и четыре ограниченные роли. Не создавать новый кластер или отдельные VM только ради этого staging. Это предложение, а не выполненное действие. Цену upgrade по аккаунту и перерыв при изменении тарифа согласовать с провайдером.

| Вариант | Публичная базовая цена / месяц | Ограничения |
|---|---:|---|
| Существующий 1 CPU / 1 ГБ / 8 ГБ, default_db | 1 200 ₽ | Одна БД и один пользователь по документации; пустота/неиспользование не проверены. Четыре LOGIN-роли для нашей схемы не подтверждены. Экономия не оправдывает запуск под gen_user. |
| 1 CPU / 2 ГБ / 20 ГБ, отдельная rehab_staging | 2 000 ₽ | Дополнительные БД/пользователи разрешены; фактические ACL, зона, TLS и возможности административной роли ещё проверить. На одном кластере сохраняется общее потребление RAM/CPU/диска. |

Ограничения: [создание БД](https://timeweb.cloud/docs/dbaas/postgresql/create-db), [пользователи](https://timeweb.cloud/docs/dbaas/postgresql/users-and-privileges). ## Безопасный reset через отдельный ящик

Подготовлен opt-in provider `staging-mailbox` и отдельный `deploy/timeweb/staging-mailbox.compose.yml`. Основной Compose продолжает использовать test/discard и network=false. Никакая доставка сейчас не выполняется.

Будущий режим принимает только staging + test payment mode + network=true + подтверждение `MIGRATION_TEST_MAILBOX_CONFIRM=dedicated-synthetic-mailbox`. Источники только из явного allowlist искусственных адресов @example.invalid; сообщения password_reset/email_confirmation перенаправляются на один приватно заданный MIGRATION_TEST_MAILBOX. Покупка остаётся discard: письмо о покупке не отправляется. Произвольные получатели/виды сообщения отвергаются. RuSender сохраняет стабильный idempotency key очереди, bounded retry и проверку origin/пути/формата ссылки. Мок-тесты проверяют маршрутизацию, одинаковый ключ повторов и запреты; сетевых вызовов нет.

После отдельного разрешения доставки: владелец создаёт отдельный защищённый ящик исключительно для synthetic аккаунтов, ограничивает доступ и отключает пересылку в общие каналы; подключает подтверждённого отправителя RuSender. В приватные переменные worker добавить MIGRATION_TEST_MAILBOX, подтверждение, уникальный MIGRATION_MAIL_NAMESPACE, RUSENDER_API_TOKEN, RUSENDER_KEY_ID, RUSENDER_FROM. API/seed продолжают использовать staging@example.invalid, настоящий адрес тестового ящика не становится аккаунтом приложения. Override не добавляется в основной manifest автоматически: будущий запуск должен явно объединить основной Compose и override; поддерживаемый способ выбора/сборки итогового manifest в Timeweb надо подтвердить до deploy. Итоговый YAML не должен содержать значения секретов.

Через HTTPS запросить reset в интерфейсе, открыть письмо только в приватном ящике/своём браузере, выполнить сброс, проверить повторное использование ссылки и отзыв старых сессий. Ссылка содержит token во fragment, приложение отправляет его в POST body; не включать body logging, tracing, session replay/аналитику на этих страницах, не вставлять ссылку в терминал, отчёт, тикет, чат или screenshot. Mail provider и ящик получают содержимое reset письма — это выбранный приватный канал, не обещание отсутствия токена у почтового сервиса. Не публиковать inbox/queue admin endpoints. Для фиксации результата достаточно success/failure и счётчиков без адресов/ссылок. После теста отключить network/override, убрать staging почтовый ключ и удалить тестовые письма по согласованной политике. Реальные аккаунты не участвуют.

## Очистка до реального импорта

1. Остановить synthetic приложение и worker, закрыть его origin, убедиться в отсутствии активных writers. Отдельно согласовать будущие разрушительные действия; сейчас ничего не удаляется.
2. При rehab_staging проверить точное имя, synthetic marker/UUID и отсутствие любых несинтетических данных; удалить всю отдельную synthetic БД только после разрешения. default_db не трогать. Создать чистую целевую БД с новыми секретами/ролями; отключить --synthetic-seed и тестовые mail/payment настройки. Не переносить очереди, сессии, reset/confirmation токены или искусственные заказы.
3. Если позднее одобрен вариант default_db, заранее сохранить перечень только создаваемых объектов и контрольное состояние. Удалять только собственную схему rehab/ledger и связанные synthetic объекты с проверенным списком зависимостей, не DROP DATABASE default_db и не слепой CASCADE. При любом постороннем объекте остановиться. После очистки сравнить каталог с исходным состоянием, проверить отсутствие synthetic UUID/заказов/писем/сессий и начать миграции с чистого ledger.
4. Реальный импорт — отдельный разрешённый этап с проверками UUID/хешей/покупок/видео. Текущий импорт защищён loopback guard; запуск на Timeweb потребует отдельного контролируемого изменения, а не обхода защиты. Размер кластера для реальных данных оценить отдельно. Не смешивать исторические unknown оплаты с test/live.

## Память и минимальный тариф приложения

Новая локальная четырёхпроцессная репетиция: вход → кабинет → synthetic checkout → восемь повторов ResultURL → доступ → выход → reset. На macOS Node20.20.2 за 9,37 s (88 отсчётов/100 ms) суммарный пик RSS frontend/API/worker — **279,70 МиБ**; отдельные максимумы frontend174,36, API59,56, worker58,83 МиБ. PostgreSQL114,22 МиБ отдельно: это DBaaS, не бюджет приложения. Общий пик не равен сумме отдельных максимумов. Браузер/harness не включены. Это короткий synthetic smoke одного пользователя, не нагрузочный тест или оценка production; RSS включает shared pages и не равен cgroup working set.

Свежая macOS сборка Next: **956,89 МиБ** суммарного RSS дерева build processes, 15,34 s, exit0. Дополнительно полный Linux Node22.23.3 build --webpack в Docker --network none, --memory 2g, --cpus 1: exit0, 48,70 s после установки зависимостей; **cgroup memory.peak 2 070 282 240 bytes = 1,93 ГиБ** при лимите2ГиБ. В peak входят установка devDependencies из offline npm cache и reclaimable page cache; это не чистый RSS Next. Первый пробный повтор из уже pruned build image дал ошибки alias resolution из-за отсутствия devDependencies; он не использован для оценки успешной сборки. Повтор с npm ci --offline --ignore-scripts прошёл. Исходная Dockerfile сборка также прошла.

**Минимум для запуска готовых контейнеров: 2 ГБ RAM** с запасом на ОС/Docker, API pools/очередь и SSR. 1 ГБ для полной сборки/запуска не рекомендован. **Рекомендованный начальный тариф для общей сборки+работы: 4 ГБ RAM**, 1–2 CPU (конкретный доступный Compose preset уточнить; 1 CPU Linux сборка проверен). Пик2ГБ плюс старые работающие контейнеры при redeploy не укладываются в безопасный бюджет2ГБ. Уточнение11.10: builder на сервере приложения, минимум3ГБ от поддержки, выбираем4ГБ. 4ГБ — консервативный запас, не доказанный нагрузочным тестом minimum. 30ГБ диск в старом Docker1/2/30 preset нельзя признать достаточным без проверки свободного места после образов/BuildKit cache; локальные source/storage не публикуются.

[Compose документация](https://timeweb.cloud/docs/apps/deploying-with-docker-compose) допускает VPC при создании и постоянные services; [управление приложением](https://timeweb.cloud/docs/apps/upravlenie-apps-v-paneli) описывает управляемый сервер и увеличение тарифа.
